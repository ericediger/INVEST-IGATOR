# INVEST-IGATOR (formerly Investment Research) 1.0 — architecture

Source of truth: investment-research-app-brief__v008__2026-09-06.md (immutable reference). This application does not use the household financial files.

Inspected the server Mac (macOS), local app README/package manifests, project AGENTS.md, and existing launchd backup convention. Existing local apps use Node 20, Express and better-sqlite3. No reverse proxy or protected remote route was established. The owner confirmed this local server is suitable. The application binds **127.0.0.1 only**, with exact Host checks and same-origin write protection. It is available to browsers on this Mac, not the LAN or internet. The operating-system account and loopback boundary provide local access; there is no claim of remote authentication. No existing app, database, port binding or service is replaced.

A separate Node/Express service serves a small accessible browser application and same-origin JSON API. SQLite WAL on local disk is authoritative. A single versioned workspace document makes complete-workspace transactions and portable restoration straightforward at household scale. SQLite stores a random optimistic revision alongside the document; all mutations compare it inside an immediate transaction. Snapshots, scenarios, decisions and company/evidence history are append-only through ordinary API routes. Complete restore is the only replacing operation.

All numerical data starts null/absent. Only the seven specified companies and their explicitly carried-forward source notes are seeded, once when the database is first initialized. Empty restored workspaces remain empty after restart.

Backups use the SQLite online backup API, not filesystem copies of live WAL databases. Pre-restore backups are made under a write transaction before replacement. Retention: latest 30 scheduled/manual backups; pre-restore backups retained until the owner explicitly removes them. Daily launchd backup follows the existing Mac convention. Backups are on this machine; off-machine disaster recovery is an explicit limitation.

Official guidance checked September 6, 2026:
- https://www.sqlite.org/wal.html — WAL requires all processes on the same host; do not deploy on network storage.
- https://www.sqlite.org/backup.html — consistent online database backups.
- https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md — synchronous transactions and backup API.
- https://expressjs.com/en/advanced/best-practice-security/ — untrusted input and production security.

## Release 1.0.1 — confirmed home-network access

The owner confirmed “Trusted home network; no login.” The installed app now binds to 127.0.0.1 and the specific private IPv4 address <lan-address>, accepting peers only in loopback or <trusted-subnet>. Each request must use an exact configured Host; writes must match that Host's Origin. No proxy trust, wildcard origin, public listener, router or firewall change is introduced. Access is deliberately shared with every trusted LAN device, with no app login or TLS. The UI reports the active boundary and identifies the server as the data location. This supersedes the initial loopback-only installation note above. Schema and persistence are unchanged.

## Release 1.1.0 — AI research service

The existing Express process now owns an optional OpenAI-backed research service. Additive SQLite tables hold settings, queued/running/completed research, captured company context, provider source references, token usage, and accepted-evidence mappings. A single in-process worker performs web research, a separate counterevidence search, and structured assessment. Follow-up questions perform their own web search with bounded company-specific history. HTTP requests enqueue durable jobs and return immediately; the browser polls progress.

The persistent right panel is mounted outside the main route-rendering element. Company page navigation updates its focus; the inbox offers historical run selection. No model-generated HTML executes. Citations are rendered from HTTP(S) source references returned by the API. Accepting a report appends an AI-authored evidence note using the same workspace revision checks as manual edits, with an idempotency mapping committed in the same SQLite transaction.

No scheduler, trade execution, portfolio suitability analysis or automatic financial snapshot ingestion is included. The first release operates on demand; see `AI-RESEARCH.md` for setup, transmission scope, usage bounds and recovery semantics.

## Release 1.3.0 — automated sector analysis

The research service gains a persisted orchestration record (`ai_analyses`) that drives ordinary `ai_runs` jobs; `ai_runs` gains a nullable `analysis_id` column (added in place on first start). A sector request creates one analysis and enqueues a `discovery` run (web search → structured candidate list, validated locally: seeds retained, tickers normalized, duplicates/limits enforced, archived companies excluded). When it completes, the service reuses or creates workspace companies for the selected candidates (ordinary `company.create` and a provenance evidence note through the existing optimistic-revision path), enqueues one `review` run per company with `withSnapshot: true`, and, when all are terminal, enqueues a `comparison` run over the completed reports and snapshots. Every transition happens in `advanceAnalysis`, invoked after each child run finishes; the state is re-read from SQLite so restarts, cancellation and failures are handled without in-memory assumptions. Restart marks queued/running runs and analyses interrupted, as before; there is no automatic retry.

The worker now processes up to `RESEARCH_AI_CONCURRENCY` runs at once (default 2, maximum 4) while still allowing one pending run per company. The daily limit counts user-started runs plus analyses, so one sector request is one run; the number of companies per analysis is bounded by the mandate setting (default 6, maximum 10) and the estimated request count is shown before starting.

Financial data collection is a two-request stage (web search → strict JSON extraction) shared by the standalone `snapshot` kind and snapshot-first reviews. The model only reports cited figures in full currency units; `server/financial-snapshot.js` validates citations, dates and currencies, discards uncited values, flags stale prices, old periods, scaled units and cross-currency mixes, and computes net debt, market capitalization (price × shares), enterprise value, margins, growth and multiples locally. `server/sector-analysis.js` builds a shared source registry for the comparison, remaps each company's citations onto it, records period/currency/freshness caveats, and validates the ranking (every analyzed company ranked once, unknown tickers dropped, omitted companies appended as Research further, Consider gated on a fresh price plus a computed multiple). The company assessment's Consider gate accepts either saved forward scenarios or an app-collected snapshot with a fresh price and multiple, recording which basis was used.

The frontend adds `public/analysis.js`: a request form, analysis history, and a dashboard (ranked recommendations, snapshot/valuation/growth tables, a single-hue bar comparison, operating metrics, per-company drill-downs, sources, data-quality and basis panels) polling the analysis document while it runs. The research panel renders snapshots, catalysts and sector-run pointers, and exposes `showRun` for drill-down. The workspace document schema is unchanged (schema 1); AI snapshots live in the research archive and are not written into manual financial snapshots.

## Release 1.4.0 — intake, dispositions and the home screen

`server/workflow.js` (`WorkflowService`) owns an additive `dispositions` table (append-only rows: company, disposition, set by app or owner, run id, rating, previous value, note, Invested details, timestamp; the latest row per company is current). It hooks `ResearchService.onRunFinished`: a completed `review` with a report is mapped by `server/dispositions.js` (Consider → Watch with highlight, Watch, Research further → Research, Pass → Declined, missing → Research) and recorded unless an owner row is in force; a run carrying a snapshot fills a blank exchange or currency on the company record through the ordinary `company.update` action and re-stamps the run's fingerprint. Owner overrides are rows with `set_by = owner`; `auto` releases them by recording an app row derived from the latest assessment. The app never writes Invested. On construction the service backfills companies without rows from their latest stored assessment or legacy status, without touching the workspace document (so the release health check still sees an identical workspace).

Intake is a new sector-style run kind (`intake`, no company) in `server/research.js`: two provider requests (web search → strict JSON) resolve owner entries to primary listings; `server/intake.js` validates tickers, currencies and citations, matches the workspace and classifies each entry as resolved, existing, ambiguous, unresolved or not a company. Entries already matching a workspace company are recognized before the run and need no provider call. On completion the workflow service reuses or creates the company (with a provenance evidence note), records a Research disposition and queues a snapshot-first review through `startRun`, which applies the key, daily-limit and queue checks shared with the HTTP route. Ambiguous entries wait for `chooseListing`. Every step is re-read from SQLite, so a restart leaves a consistent record (the intake run becomes interrupted like any other).

`GET /api/workflow/overview` joins workspace companies with their latest completed review, latest research snapshot (re-derived at read time), pending run, latest manual snapshot and disposition row into the home-screen document; counts and recent intakes ride along. The frontend adds `public/home.js` (intake box with per-entry status and choice buttons, Watch & Invested / Research / Declined / Archived tabs, rows with rating, summary, dated price, multiples, progress and the disposition control with an inline Invested form, polling while research runs) and renders the same summary on the company overview page. The old watchlist, its “DATA-CENTER SUPPLY CHAIN” header and the “Supply-chain role” wording are gone; the legacy `status` field stays in the record (hidden in the form) so the workspace schema is unchanged.

## Release 1.5.1 — home redesign (dark interface)

The stylesheet became a token system (`--bg`, `--text`, `--accent`, functional colors) applied to every page; one typeface at two weights, hierarchy by scale, text contrast at least 4.5:1, accent reserved for the primary action, links and selection. `public/home.js` renders Invested and Watch as separate sections and compact rows with a `<details>` disclosure for figures, triggers, research actions and the decision control; Research, Declined and Archived are separate views. The overview gained `freshness` (assessment age, stale after 30 days, price stale after 7), `figures.consensus` (target, upside, date) and `assessment.detail.rationale`/`valuation`; the trigger lists are the assessment's own material. The browser suite opens the disclosure before using row controls.

## Release 1.5.0 — price and financials feeds, feed-first snapshots, per-stage models

`server/feeds/` is a plain-JavaScript port of the pieces of STOCKER's market-data package this app needs: a sliding-window rate limiter with a persisted day bucket (`rate-limiter.js`), a New York market calendar with NYSE holidays (`calendar.js`), text-first HTTP handling because Tiingo answers rate limits with HTTP 200 and a plain-text body (`errors.js`), Tiingo end-of-day prices (`tiingo.js`), CoinGecko simple prices (`coingecko.js`) and SEC EDGAR XBRL company facts with a fiscal-year extractor keyed by period end so restated comparatives land in the right year (`edgar.js`). `FeedService` (`index.js`) owns additive tables for usage, price observations, company profiles (asset type, feed symbol, CIK, CoinGecko id, Tiingo coverage status), a small cache and a fetch log; runs the daily close fetch from an in-process timer (no new LaunchAgent); refuses a fetch plan that would exceed the hourly or daily quota; and collects feed blocks for snapshots. The app never calls STOCKER's API.

The research service takes the feed service as an optional dependency. A snapshot stage now starts with `feeds.collect`, merges the feed sources into the run's registry, tells the model what is already collected (`feedSummary`) and lowers the web tool-call cap when both price and financials are covered, then merges the feed blocks over the model's draft (`mergeFeedDraft`) before the unchanged `normalizeSnapshot`. The mandate gains `stageSettings` (collect / extract / analyze), stripped from the context sent to the model and applied per call through model and reasoning-effort overrides on the provider; usage records carry the role. The workflow overview prefers the newest dated price across feed observation, research snapshot and manual snapshot, and exposes the profile and feed status. Keys live in the private data folder through `scripts/configure-feeds.js` (`Connect feeds.command`); the SEC contact is mandatory for EDGAR and nothing is sent to the SEC without it.
